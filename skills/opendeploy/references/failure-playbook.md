# Failure playbook - opendeploy

Match the symptom, run the inspection, apply the action. Do not retry silently - every failure either has a root cause worth surfacing to the user or is a genuine terminal state that must be reported, not papered over.

| symptom | inspect | action |
|---|---|---|
| **401** on any call | first check `opendeploy auth guest-status --json` / `binding_state`; then inspect `~/.opendeploy/auth.json` kind byte (`od_k*` dashboard token vs `od_a*` local deploy credential) | If binding state is `pending`/`unbound`, use the bind-only row below instead. Otherwise the token was rejected. **Do not auto-delete `auth.json`.** Surface the [`401 token-rejected AskUserQuestion`](#401-prompt) defined below — never silently exit, never silently replace the credential. |
| **401 on `/v1/profile` only** | token starts with `od_a` and `auth.json.guest_id` exists | This can be normal for a local deploy credential that has not been linked to an account. Do not use `/profile` as preflight. Use `GET /v1/regions/` for auth sanity and region discovery. |
| **403 `bind_required`** on `/v1/billing/*`, custom-domain routes, or account-bound-only service operations | `auth.json.guest_id` non-empty AND no dashboard token | The current credential has not been linked to an account. Surface only the signed account-binding URL and tell the user to bind, then retry. Do not print the live app URL, health URL, project IDs, or service IDs in this response. Use the fixed bind-only block below. The skill cannot bind on the user's behalf. |
| **401/403 while `binding_state: pending` or auth state is `unbound`** | `opendeploy auth guest-status --json`, `opendeploy deploy report <id> --json`, or saved auth file with valid `guest_id` + `bind_sig` | Binding is still required. Do not keep retrying the operation and do not surface the live URL even if `/health` returns 200. Print the fixed bind-only block below with the signed bind URL, then stop until the user confirms binding is complete. |
| **403 `guest_quota_exceeded`** on service create | response body `{field, requested, limit}` | Service spec exceeds the current plan/resource ceiling. Name the field and values before asking. Ask with a structured question and make `Upgrade plan (Recommended)` first. If the user chooses upgrade, return `https://dashboard.opendeploy.dev/settings` exactly and stop mutation until they come back. If they choose to adjust resources, re-issue within the returned CPU/memory/replica limit. |
| **403 `quota_exceeded` on volume add** | response body includes `exceeded_resources` and may include `available_addons` | Persistent-volume storage quota is not available for the intended size/account. The backend has already included storage add-ons in the limit; if it still returns 403, treat it as a real storage quota block. Report current/requested/limit and matching storage add-on quantity/price when present. Do not probe smaller sizes by default. Ask with `Upgrade plan (Recommended)` first and return `https://dashboard.opendeploy.dev/settings` if chosen. Retry with a smaller volume only when the user explicitly chooses resource adjustment. |
| **409 on `POST /v1/projects`** for a local credential not linked to an account | response includes `project_id` of the existing project | One local credential without account binding -> one live project at a time. Either (a) reuse the returned `project_id` and proceed with Step 4 onward, or (b) wait for the 6h GC and retry. Don't loop. |
| **429 on `POST /v1/client-guests/register`** | response `Retry-After` | 5/hour/IP limit hit. Surface `Retry-After` to the user. Do NOT retry inside the skill. If the user can't wait, they need a dashboard token instead of a new local deploy credential. |
| **Register response missing `api_key`** | response body | Idempotent replay: same `(IP, UA)` already created a credential within 24h and the plaintext is gone. Skill cannot recover. Tell the user to restore the previous `~/.opendeploy/auth.json` or wait out the 24h window. Do not write a partial auth file. |
| **403 "subscription"** / **"quota"** | API body/CLI stderr with `exceeded_resources`; add-on prices in `available_addons` | Tell user *which* quota ran out (project count, custom domains, storage, CPU, memory, deployments, bandwidth, etc.), include current/requested/limit, and list the matching upgrade add-on with quantity and price/currency when present. Treat the backend result as authoritative because it includes active add-ons before rejecting. Ask with a structured question and make `Upgrade plan (Recommended)` first. If the user chooses upgrade, return `https://dashboard.opendeploy.dev/settings` exactly and stop mutation until they come back. Do not try to work around a billing gate unless the user chooses an explicit lower-resource adjustment. |
| **Region not found** | `opendeploy regions list --json` | `REGION_ID` is stale. Re-run region discovery, pick a fresh `active` region, and retry. |
| **`POST /v1/deployments` 400 `cannot unmarshal string ... ResourceLimits.resources.cpu_limit of type float64`** | request body | You included `resources:{cpu_request:"500m",cpu_limit:"2",...}`. Deployment-service expects **numeric** cores/GiB at `resources.*`, not K8s strings. Drop the block entirely - the service row's resources (set at Step 3.3) are authoritative. |
| **Project/service create returned an error but duplicate rows appear** | `projects list/get` by stable name, `services list/get` for the project, local `.opendeploy/project.json` | The create call probably committed before the gateway/CLI failed, or the agent tried several schema variants. Stop issuing create calls. Resolve the single intended project/service id from read-back, save context, and patch/reuse it. If multiple duplicates exist, ask which one to keep; do not delete rows with an agent token. |
| **Service create 400 `CreateServiceRequest.Type` / `Type required`** | `service.json` | The body is missing the required service `type`. Set `type` to `web` for the public HTTP service, `worker` for background workers, `cron` for scheduled work, or `static` only for static-site service mode. Read back services by stable name, then retry once with the corrected same body if no matching service exists. |
| **Service env is empty after create but plan expected env keys** | `service.json` + `opendeploy services env get <project-id> <service-id> --json` | The create body likely used a wrong alias such as `runtime_env`, `env`, or `environment_variables` instead of exact `runtime_variables` / `build_variables`. Do not upload source or create deployment. Patch env with a 0600 body file using `opendeploy services env patch ... --body ... --confirm-env-upload --json`, read back key names, then continue. |
| **Service volume was requested but read-back shows no active volume** | `service.json` + `opendeploy volumes list --service <id> --json` | Inline `volumes` may not be supported by the installed CLI/backend combo. Do not tell the user storage is attached. Add the volume through `opendeploy-volume` before first deploy, then re-list; if quota blocks it, surface the upgrade/storage choice. |
| **Deployment succeeds but DB-backed routes 500 with missing tables** | service logs + migration logs + service `start_command` + package/Dockerfile command path | Do not print the success banner. The migration command did not run or ran without all required env. Inspect ORM/schema/config for migration-only aliases such as `DATABASE_DIRECT_URL`, `DIRECT_URL`, `MIGRATE_DATABASE_URL`, `MIGRATION_DATABASE_URL`, and `SHADOW_DATABASE_URL`; patch missing aliases from the managed DB when valid. Then put the migration command in the command path the image actually runs: package `start` script for auto-builder/package-manager images, or Dockerfile `CMD`/entrypoint for Dockerfile images. Re-upload and create a new deployment. |
| **Deployment fails at `progress=10` in <2 s, `error_msg:"Service failed"`, `logs.total=0`** | `GET /v1/deployments/:id` + backend deployment-service logs when OpenDeploy support/operator access is available | Step 4.5 (`/upload/update-source`) was skipped, returned a non-2xx that was ignored, or the temp file had been GC'd before it ran. The Temporal workflow started with empty `source_path`; the build activity's `filepath.Join("", "Dockerfile")` resolves to `/Dockerfile`, which doesn't exist, so Dockerfile + auto-builder + auto-builder-without-Dockerfile all return "not found" and the workflow summarises `"Service failed to deploy"`. Re-upload (Step 4) -> bind (Step 4.5) -> retry Step 7. Verify `project.source_path` is non-empty via `GET /v1/projects/:id` before retrying. |
| **`analysis.language == ""`** | local workdir | The local analyzer couldn't identify the stack. Surface the [`empty-language AskUserQuestion`](#empty-language-prompt) so the user can pick a language, point at a Dockerfile, or cancel — do not just bail with an `exit 1`. |
| **Preflight `no_service_detected` / `no_package_or_dockerfile` but source has a clear server entrypoint** | `opendeploy preflight . --json` + manifests (`go.mod`, `pyproject.toml`, `Gemfile`, etc.) | Do not treat this as a terminal blocker. Treat it as a deployment-files decision. If the deployment files were listed in the approved plan or file-edit permission is already granted, generate a minimal root `Dockerfile` and `.dockerignore` using `dockerfile-authoring.md` and continue; otherwise ask for structured source-edit approval first. |
| **Plan picks `.devcontainer`, docs, tests, config package, or image-only sidecar as an app service** | compose/workspace manifests + Dockerfiles + service scripts | Treat this as a monorepo service-graph correction, not a blocker. Ignore dev/test/config packages, map DB/cache images to managed dependencies when supported, keep image-only sidecars as support gaps or prebuilt-image services, and continue with the highest-confidence web/API + worker graph. Do not create services for every compose entry. |
| **Wrapper/nested Dockerfile missing from build context** | `archive create` manifest + `dockerfile_path` + build logs | Deployment Dockerfiles placed under metadata dirs like `.opendeploy/` are excluded by smart packaging. Move wrapper Dockerfiles to an included path (`Dockerfile.web`, `Dockerfile.worker`, `deploy/Dockerfile.worker`), update `dockerfile_path`, re-run archive review, then retry once. |
| **Deployment `failed` at build** | `GET /deployments/:id/logs?tail=300` + `build-logs/stream` (WS -> ClickHouse) | Report root cause **verbatim** from build logs. Do not patch the app blindly. Memory: "Task polling timeout" is a frontend 5-min timeout - the build may still be progressing. Trust ClickHouse build_logs for real state, not the UI timeout. |
| **Dockerfile mode was selected but logs show auto-builder / language-provider build** | first 100 build-log lines + `opendeploy services get <id> --json` | This means the platform ignored `dockerfile_path`. Stop after one read-back verification; do not keep switching Dockerfiles or retrying. Report service `builder`, `dockerfile_path`, and the first auto-builder log line to OpenDeploy support (`hi@opendeploy.dev`). |
| **Multi-service deployment logs show the wrong image, Dockerfile, port, or Kubernetes resource for that service** | service identity matrix from setup + deployment logs + `services get/list` + `deployments list` | Treat as service mapping corruption, not an app bug. Stop normal retry/rollback loops. Do not create replacement services or stop unrelated healthy services until the user approves a recovery plan. Capture project id, expected service id/name/port/dockerfile, actual log resource/image/port, and deployment id; engage OpenDeploy support if read-back is inconsistent. |
| **Build fails with `parameter not set` for a Docker ARG** | Dockerfile `ARG` lines + `RUN` commands using `set -u`, `set -o nounset`, or `${VAR}` | This should be caught before mutation. Empty-string `build_variables` may be filtered before BuildKit, so do not keep trying empty/space/no-op variants. If one build-variable attempt still fails, ask to patch the Dockerfile with a safe default such as `ARG EXTRA_ARGS=""` or `${EXTRA_ARGS:-}` and redeploy once. |
| **Runtime says an app must not run as root** | runtime logs from apps that refuse UID 0 | First verify whether the repo already has a non-root Dockerfile variant. If that variant was listed in the approved plan, select it and redeploy once; otherwise ask before switching paths. If Dockerfile mode is ignored, stop and report the mismatch to OpenDeploy support. If no Dockerfile exists and a rootless container can be generated from clear source evidence, author it under the existing deploy/file-edit approval when covered; otherwise ask once for source-edit approval. |
| **Deployment `failed` at deploy** | `GET /deployments/:id/logs?tail=300` | Usually K8s admission failure (image pull, resource quota, missing secret). Surface the reason; if it's our resource spec, adjust via `PUT /v1/services/:id` (per-service) and retry. |
| **Multi-service deploy hits 403 quota while replacing or recovering a failed service** | quota body + `deployments list` + service identity matrix | Do not free quota by stopping healthy unrelated services first. Try `deployments retry` on the failed deployment when it can reuse the existing rollout slot after config/env has been patched. If the backend returns `exceeded_resources`, treat it as authoritative and ask with `Upgrade plan (Recommended)` or a deliberate graph reduction. If quota state looks pinned by hidden/stuck records, stop and engage OpenDeploy support instead of creating more services. |
| **Worker deployment builds but fails readiness because it listens on no port** | service type/start command + runtime logs | Do not expose the worker as the public app. Keep it as `worker`/internal. If the current platform still requires an HTTP readiness port, add the health shim directly when the deploy plan already covered worker readiness; otherwise ask once, then redeploy. |
| **Deployment hangs in `analyzing`** | `GET /v1/deployments/:id` after 60 s (the `/status` alias returns 404 via gateway) | This state is unexpected in the agent-first path. Do not call legacy analyze endpoints and do not keep retrying. Verify that source binding completed (`project.source_path` non-empty), the service was created with explicit port/build/start/Dockerfile config, and deployment creation used that service id. If those are true, report a platform workflow bug with project/service/deployment IDs. |
| **Subdomain 409 collision** | 8.1 re-check | Append a random 4-char suffix (`[a-z0-9]{4}`) to the user's prefix, retry 8.1 once. If still 409, surface the [`subdomain-collision AskUserQuestion`](#subdomain-collision-prompt) so the user can pick a new prefix or accept the random one. Never strip characters to force a fit, never just stop. |
| **Subdomain rename 404 on auto row** | 8.2 again | The auto domain row hasn't been written yet. Poll 8.2 every 2s for up to 30s. If still missing after 30s, report that deployment succeeded but ingress wiring is slow - user can retry 8.3 manually. |
| **Custom domain DNS check resolves to Cloudflare/CDN IPs or SSL challenge returns 404** | `opendeploy dns check <domain> --json` + `opendeploy domains get <domain_id> --json` | The DNS row is probably proxied or pointing at another app instead of OpenDeploy. Do not create another domain row. Tell the user to edit the existing CNAME, set Cloudflare Proxy status to DNS-only/gray cloud until OpenDeploy SSL is active, remove conflicting A/AAAA records, then re-run `dns check` and `domains get`. |
| **Upload 400 "Git validation failed"** | response body `error_code` + `available_branches` | Branch doesn't exist or credentials wrong. If `available_branches` returned, pick `default_branch` and retry. Else surface error verbatim. |
| **Upload 400 "invalid region"** | `GET /v1/regions` | Region deactivated between Preamble and Step 4. Re-pick, retry. |
| **Mutating command returns 502/503/504 after a long request** | Read back the affected object with `projects get`, `services get/list`, `volumes list`, `domains get/list`, or `deployments list` | The gateway may have timed out after the backend committed state. Do not blindly retry. Continue if read-back proves the resource exists or source/deployment changed. Retry once only when read-back proves no state changed; for source uploads, switch to multipart/split upload after one read-back-confirmed failure. |
| **Upload 504 / edge timeout** | `GET /v1/projects/:id` and source fields | Upload/bind may still have completed after the edge timed out. Do not blindly retry. Continue if `source_path` is non-empty and `original_file_size` matches. Retry only when source is empty/zero/stale; prefer multipart or split upload-only -> update-source if the CLI supports it, and ensure the file name ends in `.zip`. |
| **Build fails because `.npmrc` is missing** | archive manifest + Dockerfile/package manager logs | `.npmrc` can be required build config. Rebuild the source archive including `.npmrc` if it contains no auth material. If it contains tokens/credentials, ask for explicit consent or strip the secret first. |
| **PHP/Symfony runtime says `Unable to read .../.env`** | runtime logs + `app/config/bootstrap.php` / Symfony Dotenv `loadEnv` + local `.env` contents | OpenDeploy smart archives exclude `.env` / `.env.*` for safety, so a required committed `.env` never reached the image. If the local `.env` only contains non-secret defaults such as `APP_ENV` / `APP_DEBUG`, patch the Dockerfile or entrypoint to recreate those static lines and redeploy. Do not hand-roll an archive to smuggle `.env`, and do not print or bake secrets into the image. |
| **Build fails because Corepack installed a newer package manager than the repo expects** | Dockerfile + `package.json.packageManager` + build logs mentioning `corepack`, `pnpm`, `yarn`, or `node:sqlite` | This should be caught before mutation. If `package.json` pins `pnpm@9.x` but Dockerfile runs `corepack use pnpm` / `pnpm@latest` on Node 20, patch to the pinned package-manager version under the existing deploy/file-edit approval when covered; otherwise ask once, then redeploy. Prefer pinning the package manager to repo evidence over upgrading Node unless repo evidence requires a newer Node. |
| **Clean cloud install resolved a newer dependency and source imports break** | no lockfile + package manager logs + missing export/module error | Treat this as `dependency_resolution_not_locked`. Before any further redeploy, ask whether to generate/commit a lockfile, pin the affected dependency, or proceed knowingly. Do not keep retrying OpenDeploy; the same clean install can fail anywhere. |
| **Build fails because files under `build/` are missing** | archive manifest + build logs naming the missing path | Do not assume every `build/` directory is generated output. If Dockerfile, Makefile, generators, or package scripts reference it, treat it as source and rebuild the archive with that directory included. |
| **Build needs Git metadata but `.git` is excluded** | `archive_manifest.git_metadata`, Dockerfile `--mount=type=bind,source=.git`, `git describe`, or version script logs | CLI `0.1.19+` should catch this before upload. Keep excluding `.git` by default, especially in agent worktrees where `.git` is often a pointer file. Prefer setting `GIT_COMMIT`, `APP_VERSION`, or `SOURCE_VERSION` build variables from local `git rev-parse` / tags. Upload `.git` only with explicit user approval. |
| **Build fails during `COPY . .` / broad context copy with local agent paths** | build logs naming `.agents`, `.claude`, `.codex`, `.opendeploy`, `.gstack`, or similar | Patch `.dockerignore` to exclude local agent metadata plus sensitive/debug OpenDeploy subpaths, re-run the archive manifest, then redeploy once. Do not add a blanket `.opendeploy/` rule to `.gitignore`; `.opendeploy/project.json` is safe shared team deployment context. These paths are not application source and should not be uploaded. |
| **Build or migration fails on a missing DB extension** | migration logs + search for `CREATE EXTENSION`, `enable_extension`, `pgvector`, `postgis`, `citext`, `uuid-ossp`, `pg_trgm` | If the feature is optional, ask to disable that plugin/module and continue on OpenDeploy. If it is core app functionality, engage OpenDeploy support for dependency extension support. Do not keep retrying the same migration. |
| **Managed dependency env contains placeholder secrets** | `dependencies env/status` `placeholder_secret_keys`, env value audit + app env contract | Stop before service creation only if a consumed key, generated connection URL, or synthesized consumed alias would carry a placeholder like `changeme`, `password`, or `secret`. If placeholders are unused aliases and the consumed canonical key such as `DATABASE_URL` is real, continue with a key-only warning. |
| **Managed DB catalog version is older than app docs mention** | app docs/config + `opendeploy dependencies list --json` / catalog version | Not a default blocker. Do not assert compatibility from memory; surface the version difference as a verification note, continue with the available managed DB, and verify with a targeted smoke test. Pause only when source evidence says the app explicitly refuses that version or the user asked for an exact DB version. |
| **Background dependency monitor exits 1 but later status is running** | monitor output + `opendeploy dependencies status <project-id> --json` | Watcher bug, not dependency failure. The monitor likely used `jq -e`, `grep`, or a status-change predicate that exits 1 while still waiting. Continue if read-back says `running`; update future monitors to exit 0 for `pending`, `deploying`, unchanged status, empty reads, and transient read errors. |
| **App returns 5xx and runtime logs say `Access denied for user 'admin'@<pod-ip>` or `'app_user'@<pod-ip>` (MySQL) / `password authentication failed for user "app_user"` (Postgres)** | `dependencies status --json` key names + `connection_info`; use `--show-secrets` only after explicit secret-reveal approval | The dep template injected literal placeholder credentials (`admin` / `changeme` / `app_user`). Do not retry. Generate explicit credentials in a 0600 body and run `opendeploy dependencies update-connection "$PROJECT_ID" "$PROJECT_DEPENDENCY_ID" --body .opendeploy/db-conn.json --json`, then `opendeploy dependencies wait`. If the dep's reported env still shows old placeholder key names or connection_info disagrees, the env-vars JSON cache is stale (known backend bug). Patch the consuming service env with a 0600 body file, never argv: `opendeploy services env patch "$PID" "$SID" --body .opendeploy/service-env-fix.json --confirm-env-upload --json`, then create a new deployment for that service. Report the backend bug with project_id + dependency_id. |
| **Redis runtime says `invalid username-password pair` or `user is disabled`** | runtime logs + `dependencies status/env` + whether `dependencies update-connection` was used | Do not keep rotating Redis passwords or redeploying. If no rotation happened, try one URL-shape correction using the exact returned values (`redis://:PASS@host` vs `redis://default:PASS@host`, optional `/0`). If the failure happened after Redis `update-connection`, treat it as a platform Redis ACL/env sync bug. Ask the user to recreate the Redis dependency from the dashboard, or engage OpenDeploy support with project/dependency/service/deployment IDs. |
| **`POST /v1/dependencies/create` returns `400 Invalid dependency_id format`** | request body | `dependency_id` requires the catalog UUID, not the friendly name (`mysql`, `postgres`, etc.). Run `opendeploy dependencies catalog --json` (CLI `0.1.20+`) to look up the UUID. On older CLIs, fall back to the raw API: `curl -H "Authorization: Bearer $TOKEN" "${OPENDEPLOY_BASE_URL}/v1/dependencies"` and pick the `id` for the matching `name`. Save the UUID for reuse. |
| **`opendeploy services restart` returns `HTTP 503 Service Unavailable`** | `monitoring restart-status` if available, else wait | A previous restart workflow for this service is still running. Wait 10–15s and retry. Do not fall through to redeploy; the next `restart` call usually succeeds. |
| **Canonical DB URL disagrees with alias keys / `connection_info`** | `dependencies status --json` `connection_info.username/database` vs user/db parsed from `DATABASE_URL` / `MONGODB_URI`; runtime log `password authentication failed for user "<placeholder>"` or `role "<placeholder>" does not exist` | Backend env-injection bug — the canonical key was synthesized with placeholder parts (e.g. user `app_user`, db `<project_name>`) while the actual pod runs as the user shown in `connection_info`. Do **not** redeploy hoping it fixes itself. Either (a) `services env patch` the canonical `DATABASE_*` / `MONGODB_*` keys to values copied from the alias group (`POSTGRES_USER`, `POSTGRES_PASSWORD`, `PGDATABASE`, `MONGO_USER`, etc.) with `--confirm-env-upload`, then redeploy (the env layer may re-inject placeholders so a Dockerfile-side override is more durable), or (b) edit Dockerfile `CMD` / `start_command` to `sh -c 'export DATABASE_URL="postgresql://${POSTGRES_USER}:${POSTGRES_PASSWORD}@${POSTGRES_HOST}:${POSTGRES_PORT:-5432}/${PGDATABASE:-${POSTGRES_DB}}" && exec ...'` so the runtime always wins. Report the project_id + dependency_id as a backend bug. |
| **Dependency `status == "failed"`** | `GET /dependencies/status/:project_id` | DB provisioning failed. The skill cannot delete the failed row (SKILL.md rule 17 — `DELETE` is gateway-blocked for `od_*` Bearer tokens), so the retry path always runs through the dashboard: surface the [`dependency-failed AskUserQuestion`](#dependency-failed-prompt). Even on the **first** failure, the user has to remove the row from `${OPENDEPLOY_BASE_URL%/api}/projects/$PID/dependencies` before the skill can re-run setup.md Step 3.2 — the skill polls `GET /dependencies/status/:project_id` until the failed row is gone, then continues. Always print the Contact block when the user picks "Stop and contact us". |
| **Service stuck in `building` > 20 min** | `build-logs/stream` (WS) | Usually an infinite loop in user build scripts or OOM. Surface last 200 ClickHouse lines, then raise the [`stuck-build AskUserQuestion`](#stuck-build-prompt) (Wait another 5 min / Cancel deployment / Tail more logs). Do not auto-cancel without explicit consent — the build may be one slow `npm install` away from progressing. |
| **Progress endpoint remains at 10% but logs show later phases** | `deploy progress` + `deployments logs` / build-log stream | Treat logs as the phase source of truth. Tell the user what phase logs show (dependency install, image export, push, Kubernetes rollout) instead of calling it stuck solely because the percent is stale. |
| **Dockerfile exposes multiple ports and chosen port is 22/25/etc.** | Dockerfile `EXPOSE`, compose ports, runtime logs | Choose the HTTP listener for OpenDeploy ingress. Surface unsupported secondary protocols such as SSH/SMTP/raw TCP before deploy; disable only with user approval or report that the platform cannot expose them. |
| **App declares `VOLUME` / persistent runtime files** | Dockerfile, compose volumes, docs, env keys | Pause before mutation and ask for the OpenDeploy storage strategy. Recommend `Attach OpenDeploy volume` for local uploads, backups, media, SQLite, file queues, repo storage, indexes, or other fixed filesystem paths, including demos/templates that accept new uploads or generated media. Do not make ephemeral the recommended option for those apps; it is only a throwaway choice after explicit data-loss acceptance. Offer object-storage env only when the app is already designed for external object storage. For a new service, include `volumes` inline in `service.json` on `services create` (no downtime). For an existing service, route to `opendeploy-volume` (first volume triggers a Deployment→StatefulSet conversion with ~30s downtime). Postgres persistence does not preserve files such as uploads, repo data, media, indexes, or generated keys — those need object storage or a service volume. |
| **Installer/admin lock set but no admin/bootstrap exists** | service env + app docs/logs | Do not set installer-lock/setup-complete env automatically. Either provision supported admin/bootstrap state, leave setup enabled, or ask the user to approve that setup choice before retry. |
| **Generated URLs use localhost or wrong domain after success** | service env and app UI/smoke test | The app has late-bound URL/domain env. Patch known repo-referenced keys such as `APP_URL`, `BASE_URL`, `ROOT_URL`, `SITE_URL`, `PUBLIC_URL`, `CANONICAL_URL`, `SERVER_URL`, `WEB_URL`, or nested `__ROOT_URL` / `__DOMAIN` to the live URL, then create a new deployment if this was planned or approved. |
| **Runtime fails startup validation because a URL env is empty or syntactically invalid** | runtime logs + source search for `new URL`, schema/env validators, or config bootstrap | Treat it as startup-critical env missed by planning. Patch a real service URL, valid boot placeholder, or approved omission when source evidence shows the feature is disabled, then use `deployments retry` or a fresh deployment so the env snapshot updates. Do not learn one missing URL key at a time through repeated CrashLoops. |
| **Env patch read-back is correct but running app still sees old value after restart** | app redirect/logs, service env read-back, deployment version | Restart did not refresh pod env. Create a new deployment for the same service and source. For future late-bound URL or dependency env patches, prefer `Patch env + redeploy (Recommended)` instead of restart. |
| **Redeploy succeeds but static site still shows old CSS/JS/images/PDFs** | custom `nginx.conf` / `default.conf`, response headers from `curl -I`, and whether asset filenames are content-hashed | This is usually browser/CDN caching, not a failed OpenDeploy build. If Nginx config applies long `expires`, `Cache-Control: public`, `max-age`, or `immutable` to non-fingerprinted files such as `app.js`, `style.css`, `main.css`, or reused PDFs/images, patch the cache policy directly when that fix was in the approved plan; otherwise ask once with `Patch Nginx cache policy (Recommended)`. HTML should be `no-store`/`no-cache`; mutable non-hashed CSS/JS/JSON/PDF should be `no-cache, must-revalidate`; keep long `immutable` only for content-hashed asset paths. Re-upload and create one new deployment, then verify headers with `curl -I`. Do not keep redeploying the same cached config. |
| **`services list/get` disagrees with `deployments list` or version routes for a service** | direct `services get`, `services list`, `deployments list`, `services versions current/list` | Treat the visible service graph as inconsistent. Do not use rollback as a config repair and do not assume a replacement service is safe. Capture both views, keep already-healthy URLs untouched, and engage OpenDeploy support unless the user explicitly approves a replacement-service recovery path. |
| **OpenDeploy health is green but public edge returns 502/503 and app logs do not see requests** | `services health/status`, `domains list/get`, public `curl`, service logs | This is likely route/ingress convergence or edge binding, not an app crash. Do not keep rebuilding or renaming repeatedly. Verify the domain points to the intended service, wait briefly for reconciliation, and engage OpenDeploy support with project/service/domain IDs if it persists. |
| **Rollback returns 200 but no `deployment_id`** | rollback response + `deployments list` + `services get` + `services versions current/list` | Treat as rollback false-success. Version metadata may have flipped, but no rollback deployment was created and traffic was not proven to move. Do not report success. Collect the response body and read-back state, then report a backend bug; retry only after a backend fix or explicit user direction. |
| **Any 5xx** | gateway + downstream service name in error body | For mutating requests, use the read-back row above before retrying. For read-only requests, retry once after 5s. If it repeats, stop and surface the gateway's reported service. |

## Hard rules

- **Never `--no-verify` / bypass** signature or validation errors to get past them.
- **Never auto-retry on 403** (quota/subscription). It doesn't resolve itself.
- **Never delete a project to "clean up"** on failure unless the user explicitly asks. Failed state is diagnostic; scrubbing it loses evidence.
- **Never continue to Step 8 if Step 7 ended in `failed`** - a domain bound to a dead deployment is worse than no domain.
- **Always update the deploy-attempt record before retrying or stopping.** Use `references/deploy-attempt-record.md`, pick a stable `error_category`, store redacted log evidence, root cause, fix applied/planned, and terminal result. Do not invent project-specific categories.
- **Always print the Contact block (below) on terminal failure.** Every reference that can end in a `failed` / `cancelled` / `rolled_back` / unrecoverable state (deploy.md Step 7, setup.md DB provisioning, domain.md Step 9.5) must surface this block verbatim, with the listed identifiers filled in. If the user explicitly asked to engage OpenDeploy support, get a private Discord URL first with `opendeploy oncall status --json`; if no channel exists, run `opendeploy oncall setup --json` and use `authorize_url`. Discord URLs must be clickable Markdown links, not code blocks or inline code. Do not paraphrase the labels, do not drop fields, do not add emojis — the format is the contract.

## Contact block — print verbatim on terminal failure

Print the following Markdown block exactly, with the placeholder values substituted from the current context. Do not wrap the emitted contact block in a fenced code block; the fence below is documentation only. If `<PRIVATE_DISCORD>` is a returned `discord_url` or `authorize_url`, render it as `[Open private OpenDeploy Discord channel](<URL>)` or `[Open Discord authorization link](<URL>)` with the exact URL as the link target. If a value is unknown (e.g. `DEPLOYMENT_ID` before Step 7 returns), keep the label and write `n/a`. If the user did not ask to engage support yet, set `<PRIVATE_DISCORD>` to `Ask me to engage OpenDeploy support and I will return your private Discord link.` Print this **after** the per-symptom diagnostics (logs / build output / playbook hint), not in place of them — the contact block is the trailing handoff, not the only message.

```text
---

## Need help?

This deployment didn't make it. If the diagnostics above don't make the
root cause obvious, reach out and we'll look at it together — we read
every message and respond fast.

- **Private Discord:** `<PRIVATE_DISCORD>`
- **Email:** hi@opendeploy.dev

When you contact us, please paste the block below so we can jump
straight to your deployment:

- **Project:** `<PROJECT_NAME>`
- **Project ID:** `<PROJECT_ID>`
- **Service:** `<SVC_NAME>`
- **Service ID:** `<SERVICE_ID>`
- **Deployment ID:** `<DEPLOYMENT_ID>`
- **Status:** `<STATUS>`
- **Log file:** `<OD_LOG_FILE>`
- **Attempt record:** `<ATTEMPT_RECORD_PATH>`
```

`<OD_LOG_FILE>` is the absolute path to today's audit log (e.g. `~/.opendeploy/logs/2026-04-28.log`). The user may attach the file or grep it for the deployment id (`jq -c --arg d "<DEPLOYMENT_ID>" 'select(.deployment_id==$d)' <OD_LOG_FILE>`); secrets are guaranteed not to be in there.
`<ATTEMPT_RECORD_PATH>` is the local `.opendeploy/attempts/...json` record
created by `references/deploy-attempt-record.md`; write `n/a` only when the
skill could not create one.

Do **not** print the contact block on transient retryable errors (a single 5xx that resolves on retry, a 429 with `Retry-After`, an in-progress `building` state). Print it only when the skill has stopped trying.

## Where to look for logs

- **Skill operation log (local audit trail)** -> `~/.opendeploy/logs/<UTC-date>.log` (JSONL, daily roll). The first thing to consult on any user-reported "what did the skill just do?" question. Useful one-liners:
  - Recent failures: `tail -n 200 ~/.opendeploy/logs/$(date -u +%Y-%m-%d).log | jq -c 'select(.level=="error")'`
  - Per-deployment timeline: `jq -c --arg d "<deployment_id>" 'select(.deployment_id==$d)' ~/.opendeploy/logs/*.log`
  - Last deploy wall-clock: `jq -c 'select(.step=="deploy.terminal") | {ts, deployment_id, status, duration_seconds}' ~/.opendeploy/logs/$(date -u +%Y-%m-%d).log | tail -1`
  - Secrets are guaranteed not to be in here — the logger drops `api_key` / `bind_sig` / `password` / `token` / `*secret*` keys at write time.
- **Build logs** (long, full build output) -> `GET /v1/deployments/:id/build-logs/stream` (WebSocket, ClickHouse-backed, persistent). Memory: ClickHouse `build_logs` is authoritative for build phase.
- **Deploy / runtime logs** -> `GET /v1/deployments/:id/logs/stream` (SSE) or `GET /v1/deployments/:id/logs?tail=N` (one-shot).
- **Service container logs after deploy** -> `GET /v1/projects/:id/services/:sid/logs` (one-shot, project-service) or `.../logs/stream` (SSE). Memory: container stdout goes through Loki for ~hours, then gone - grab fast on failure.
- **Analyze-stage / instant-fail failures** -> both `GET /v1/deployments/:id/logs` (`logs:null,total:0`) and ClickHouse `build_logs` are **empty** for failures that happened before the build activity wrote anything. Ground truth is the backend deployment-service log for the target environment. Ask OpenDeploy support/oncall for those logs, or use the operator-provided backend log access if you are explicitly debugging the platform. Look for the line sequence `executeInitialDeployment called` -> `Temporal Workflow Input built` (verify `source_path` is non-empty) -> `Temporal workflow started`.
- **"Where is the gateway log route?"** - `GET /api/v1/logs/deployment/:id` listed in `Backend/API.md:242` returns `404 page not found` through the gateway in dev; it is not wired up. Use the dev-box `docker logs` approach above instead.

## AskUserQuestion prompts (canonical)

The matrix above references these by anchor. Each row that hands control back to the user **must** surface the matching `AskUserQuestion` — never a bare `exit 1`, never a printed "please do X then re-run" without a prompt. SKILL.md Execution rule 16 is the global obligation; the prompts below are the per-symptom shapes.

### <a id="401-prompt"></a>401 token-rejected prompt

> Question: `"opendeploy's saved credential was rejected. How do you want to proceed?"`
>
> Body (verbatim — substitute `<KIND>` with `dashboard token (od_k*)` or `local deploy credential (od_a*)` based on the kind byte at `auth.json.api_key[3]`):
> > The credential at `~/.opendeploy/auth.json` (`<KIND>`) returned `401` against the gateway. The skill will not silently delete or replace it — that decision is yours.
>
> Options:
> - `Paste a fresh dashboard token` — surface a follow-up `AskUserQuestion` collecting the new `od_k*` value, write `{"version":1,"api_key":"<NEW>","gateway":"<OPENDEPLOY_BASE_URL>"}` to `~/.opendeploy/auth.json` (mode `0600`), retry the failed call once.
> - `Open the dashboard so I can rotate` — print the dashboard API-keys URL (`${OPENDEPLOY_BASE_URL%/api}/account/api-keys`) and exit `0` so the user can rotate and re-run the deploy.
> - `Delete this credential and start fresh` — `rm ~/.opendeploy/auth.json`, then jump to `auth.md` → "Consent gate" so the new-credential AskUserQuestion fires immediately. Emit `od_log warn auth.deleted_by_user kind "<KIND>"`.
> - `Cancel` — exit `0`, leave the file untouched, no further mutations.

### <a id="empty-language-prompt"></a>Empty-language prompt

> Question: `"opendeploy couldn't identify the stack. Pick how to proceed:"`
>
> Body (verbatim — list the top entrypoint candidates the local analyzer found, one per line, with relative paths):
> > `analyze-local.md` ran but returned `language=""`. Either there is no recognizable lockfile / manifest at the source root, or the entrypoint is in a non-standard location.
> >
> > Candidates the analyzer noticed:
> > `<ENTRYPOINT_HINTS>`
>
> Options:
> - `Specify a language` — surface a follow-up `AskUserQuestion` listing `node` / `python` / `go` / `ruby` / `java` / `php` / `rust` / `dotnet` / `static` / `Other (free-text)`, then re-run Step 2 with the user's choice forced into `analyzer.json.language`.
> - `Point me at or add a Dockerfile` — surface a follow-up free-text prompt for an existing path inside the source tree (relative), or a structured source-edit approval option when local evidence is enough to generate one. If an existing path is not source-root `Dockerfile`, explain that current first deploys should use a root Dockerfile and ask before changing source root or copying/renaming it unless that choice was already listed in the approved deploy plan. If generating a new Dockerfile, follow `references/dockerfile-authoring.md`, list the exact files, and edit under the existing deploy/file-edit approval when covered.
> - `Cancel` — exit `0`, no upload.

### <a id="subdomain-collision-prompt"></a>Subdomain-collision prompt

> Question: `"<USER_PREFIX>.opendeploy.site is taken. Pick another or accept a random suffix."`
>
> Body (verbatim — `<RANDOM_PREFIX>` is the suffixed prefix the skill already retried once):
> > Both `<USER_PREFIX>.opendeploy.site` and `<RANDOM_PREFIX>.opendeploy.site` (auto-suffixed retry) are unavailable. Pick a different prefix or accept the next random one.
>
> Options:
> - `Use the random prefix on retry` — recompute a fresh 4-char suffix, retry 8.1 once. If still 409, re-surface this prompt (do not loop more than 3 times — emit `od_log warn domain.subdomain_collision_loop` after the third).
> - `Pick a different prefix` — surface a follow-up free-text prompt validating against `[a-z0-9-]{3,32}`. On answer, retry 8.1.
> - `Skip the rename, keep the auto subdomain` — the deployment is already live on the random `<random>.opendeploy.site` from Step 7. Print that URL as the final report and exit `0`.

### <a id="dependency-failed-prompt"></a>Dependency-failed prompt

> Question: `"<DB_ENGINE> provisioning failed. Delete the row in the dashboard so I can retry?"`
>
> Body (verbatim — `<DB_ENGINE>` is `postgres` / `mysql` / `mongo` / `redis`; substitute `$PID`, `$DEP_ID`, and the failure reason from `dep.error_msg`):
> > `POST /v1/projects/$PID/dependencies/` returned `status=failed` for `<DB_ENGINE>` (dependency `<DEP_ID>`). Reason: `<DB_ERROR>`.
> >
> > **The skill cannot delete the failed row** — agent credentials are blocked from `DELETE` (SKILL.md rule 17). To retry the same engine, open `${OPENDEPLOY_BASE_URL%/api}/projects/$PID/dependencies` and remove the row labeled `<DB_ENGINE>`; the skill will then re-run setup.md Step 3.2.
>
> Options:
> - `I deleted it — retry the same engine` — poll `GET /v1/dependencies/status/$PID` once every 5s for up to 60s; once the failed `<DEP_ID>` row is gone, re-run setup.md Step 3.2 with the same engine. If still present after 60s, re-surface this prompt with `body += "\n\nI still see <DEP_ID> in the project — refresh the dashboard and confirm the delete completed."`. Do not loop more than 3 times — emit `od_log error dependency.delete_handoff_loop` after the third attempt and switch to `Stop and contact us`.
> - `Switch engine` — surface a follow-up `AskUserQuestion` listing the other supported engines. The skill will print one line `opendeploy: open ${OPENDEPLOY_BASE_URL%/api}/projects/$PID/dependencies and delete the failed \`<DB_ENGINE>\` row first; once it's gone the skill will create the new \`<NEW_ENGINE>\` row and adjust env vars`, wait for the user to confirm, poll `GET /v1/dependencies/status/$PID` until the failed row is absent, then re-run Step 3.2 with the new engine. The skill will warn that downstream service `env_vars` may need adjustment.
> - `Skip the DB and deploy without it` — clear the dependency from the analysis, drop matching `DATABASE_URL` / `MONGO_URL` / `REDIS_URL` from `runtime_variables`, and continue to Step 4. The failed row is left in place for the user to inspect or remove from the dashboard at their leisure. The deployed service will start in degraded mode if it expects those vars.
> - `Stop and contact us` — print the Contact block (above) verbatim with `<STATUS>` = `dependency.failed` and exit `1`.
